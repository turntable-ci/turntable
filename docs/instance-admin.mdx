---
title: Instance administrator
description: A token for the person who runs the instance, for the few settings that belong to no org.
---

Some settings are not an org's to change: the limits that stop one org taking the instance (quotas), and the instance's own health. Until now they were reachable only on the host. The **instance administrator** is a separate principal for them, over REST.

## What it is

- A token with the prefix `tti_`, a different shape from every org token (`tt_`), so the two are told apart before any lookup and a leaked one is recognisable.
- Minted only on the host, with `turntable token create --instance --name <name> [--expires-days 30]` (1 to 90 days; the secret is shown once, only its hash is stored, in its own table). No org token of any role can mint, list or revoke one: `token list --instance` and `token revoke <id> --instance` are host commands too. The one operation that touches them is rotation (below). Minting, revoking and rotating are audited in the system org's chain.
- It holds **no org grant**. It cannot read a run, a log or a secret, and every org operation refuses it. It can call the instance operations, and nothing else.
- Accepted over **REST only**. The MCP endpoint and the realtime socket do not treat a `tti_` token as a credential, and none of the instance operations is an MCP tool.

The release lane's configuration is not an instance-token operation: it is done by an owner of the operator org in the web app, with a passkey step-up (see [Hosted setup (no shell)](/release-lane#hosted-setup-no-shell)). A `tti_` token is refused there.

`max_concurrent` can only lower an org's concurrency below the instance's per-org cap (`--org-cap`): a value above it is refused, and removing it falls back to the cap. Instance operations take no `org` or `project` field. A change is audited twice: in the system org's chain (who held the token) and in the target org's own chain (so its operators see who changed their limits).

`instance_doctor` returns the checks of `turntable doctor` (see [Doctor](/doctor)) as names and states only: each check's id, area, status, a fixed summary and a fixed fix. Raw error text and secret values are never in it, so a hosted instance with no shell can confirm a master-key rotation from it.

`instance_audit_verify` takes no key from the caller: it checks each anchor's signature under the org's audit key in the secret store, so a server with no master key answers as unavailable. Anchors kept off the server are the point: export them with the audit export sink and keep them elsewhere. REST only, never an MCP tool, and no org token can call it.

## Adding a tenant on a hosted instance

With no shell, a second org needs no redeploy:

1. `create_org` with the new org's `slug` and `name`. The org starts with no projects and no tokens.
2. `create_org_token` for that slug, with the role the tenant's first operator needs (at most `release_operator`) and an expiry. Hand the secret over once: it is not stored and cannot be read again. `kind` defaults to `person`, the operator's own token, which may approve under `untrusted_run_approval = no_agents`.
3. `create_project` for each repo the org will ingest.

`create_org_token` is a one-shot, like the env bootstrap: it works only while the org has no active token (not revoked, not expired, project-scoped ones included), so it can never add access to an org that already has some. For an org that ever had a token, even a revoked or expired one, it is refused until the `org_remint_delay_hours` setting (default 24, minimum 1; `TURNTABLE_ORG_REMINT_DELAY_HOURS`, `org_remint_delay_hours` in `turntable.toml`, or `instance_set_setting`; a value in the environment or the file locks it) has passed since the last of its tokens was revoked or expired, and the refusal says when it becomes possible. This stops a stolen instance token from getting an org's tokens revoked and minting itself a new one at once. A brand-new org with no token ever is served at once. Each re-mint emits an `org.token_reminted` event to the org, and revoking the last active token of an org emits `org.tokens_exhausted`; both are on the org's feed and reach its webhooks, and a re-mint is audited in the system org's chain and in the org's own. A token that merely expires does not emit an event, because nothing runs at that moment; the org's token list shows it as expired. After that the org's own admins manage its tokens. The system org is never a target of either operation. Both are audited in the system org's chain and in the new org's own, and no audit entry holds the secret or its hash. Neither is an MCP tool.

## Bootstrapping with no shell

A distroless image has no shell, so `token create --instance` cannot run on it. Set the sha256 of a token instead. The token never leaves your machine.

```sh
# 1. On your own machine: the token goes to stdout, its hash to stderr.
turntable token generate --instance > instance-token.txt
# Without the binary: t="tti_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=\n')"; printf %s "$t" | sha256sum

# 2. On the server, set ONLY the hash. Never the token.
TURNTABLE_INSTANCE_BOOTSTRAP_TOKEN_SHA256=<the hash>

# 3. After the first boot, call the rotation once with the token, keep the new secret, and unset the variable.
curl -fsS -X POST -H "Authorization: Bearer $(cat instance-token.txt)" "$URL/api/v1/instance/tokens/rotate"
```

- **Only when there is no active token.** On boot the hash is registered only if the instance has no *active* instance token, meaning one that is neither expired nor revoked. Otherwise it is ignored, with one log line: `instance bootstrap hash ignored: an instance token exists`. An expired or revoked token does not block, so a lapsed token never locks you out.
- **A hash registers once, ever.** A hash that was registered before is refused whether that token is active, expired or revoked, with a distinct log line: `instance bootstrap hash refused: that hash was already registered once`. It is never renewed. To recover after a token lapses, generate a new token offline and set its new hash.
- **Idempotent.** The same hash on every boot is the same row, never a duplicate.
- **Short-lived.** The token expires in 30 days at most. `TURNTABLE_INSTANCE_BOOTSTRAP_EXPIRY_DAYS` (1 to 30) can lower that and never raise it. It is audited as `instance_bootstrap_token_registered` in the system org's chain, without the hash.
- **Never logged.** Neither the hash nor a token appears in any log line. A malformed hash stops the boot with a message that does not repeat the value. The old name `LONGSHORE_INSTANCE_BOOTSTRAP_TOKEN_SHA256` still works, with a deprecation warning.
- **Rotate, then remove the variable.** Rotation is an instance operation over REST and the CLI, never on MCP: instance tokens are not MCP credentials. It mints a new token (secret shown once, hash stored) and revokes the caller's token, in one transaction. After that the variable does nothing, so remove it.

Instance tokens are always the operator's: they hold no org role and can't approve runs, so there is no `kind` field.

## Sandbox limits

The scheduler's caps and the Daytona provider's limits are instance settings, so you change them with no restart: `scheduler_global_cap`, `scheduler_org_cap`, `provider_daytona_max_live` and `provider_daytona_cpu_limit`. Set them in the web UI's instance settings page, or with `instance_set_setting` over REST (instance administrator only; no MCP tool sets them). The old variables (`TURNTABLE_GLOBAL_CAP`, `TURNTABLE_ORG_CAP`, `--global-cap`, `--org-cap`) and the provider config's `maxLive` and `ownerCiPreflight.cpuLimit` still work, as locks: a value set there shows as read-only with its source, and `set_setting` is refused with the variable named. `doctor` warns about each limit locked by an environment variable.

The settings page also shows the effective concurrency: the lower of the global cap and the Daytona `max_live` (which applies when Daytona runs the jobs), with the org cap and the vCPU limit beside it. Agents can read the same over MCP with `sandbox_limits` (read-only: the four limits with source and lock). `provider_daytona_max_live` accepts 1 to 500 in the setting and in the provider config, and a value written to the database is validated then, so it can never fail a boot. The vCPU preflight (`provider_daytona_cpu_limit`) is the real capacity guard.

- The claim loop and the provider read the value at claim and create time, cached for a few seconds. Raising a limit takes effect on the next claim. A change made on another server process shows within that time.
- Lowering a limit never stops a running job or sandbox. New claims and creates wait until usage is under it.
- `set_quotas` and project `max_concurrent` are refused above the live `scheduler_org_cap`.
- Every change is audited in the system org's chain with the old and new value.

## Backups

The image is distroless, so there is no shell to copy the database with. `db_backup` (or `turntable db backup [--keep <n>] [--data-dir ./data]` on the host) writes a consistent copy of the SQLite database with `VACUUM INTO` to a new file, `<data-dir>/backups/turntable-<time>-<version>.db`, and returns its path, size and sha256. Writes in flight do not matter: the copy holds every committed row and none of the uncommitted ones, and it is integrity-checked before it is kept.

- **Where it writes:** always a new file under `<data-dir>/backups/`. The operation takes no path. A backups directory that is a link, or resolves outside the data dir, is refused.
- **Retention:** the newest `keep` files stay (`--keep`, the `keep` input, or the `backup_keep` setting: `TURNTABLE_BACKUP_KEEP`, `[backup] keep` in `turntable.toml`, or `instance_set_setting`, default 10; see [Settings registry](/configuration#settings-registry)); older `turntable-*.db` files there are deleted. Other files are left alone.
- **Space:** refused when the free space is below twice the database size (the file plus its write-ahead log).
- **The event loop keeps serving:** the copy runs on a worker thread whose code is embedded in the binary, so heartbeats, log streaming and API calls carry on while a large database is copied. It still reads and writes disk, so expect some I/O load.
- **Before a migration:** set `TURNTABLE_BACKUP_BEFORE_MIGRATE=1` and the server takes a backup at boot, only when migrations are pending on an existing database and before they run (the file name ends in `-pre-migrate`). If the backup fails, the server does not start. It is off by default.
- **Postgres:** refused, with a pointer to `pg_dump`. Use your platform's snapshots or `pg_dump`.
- **Access and audit:** instance administrator only (a `tti_` token over REST, or the host CLI), never an MCP tool. Each backup is audited in the system org's chain.
- **Restore:** stop the server, replace `turntable.db` with the backup file (and delete the old `turntable.db-wal` and `turntable.db-shm`), start it. There is no live restore.

## In the web UI

The web UI has an instance-administrator area at `/-/instance`. It is a separate sign-in, not part of an org session.

- **Its own sign-in.** Paste a `tti_` token on the "Instance administrator" screen. The token is checked with `instance_whoami`, kept in this tab only (its own `sessionStorage` key, never a URL or `localStorage`) and used for instance routes only. It is never sent to an org route, to `/mcp` or to the realtime socket, and the org token is never sent to an instance route. An org session does not open the area, and the area needs no org session.
- **Every action is an instance operation.** Nothing is decided in the browser. A refusal (a locked setting, a value above the per-org cap, a conflicting slug) is shown word for word as the server wrote it.
- **Settings.** Generated from `instance_list_settings`, as the org and project pages are from `list_settings`: effective value, a source badge (`env`, `toml`, `ui/db`, `default`), the lock text for a value set by the environment or `turntable.toml`, and a reset to default. A save is `instance_set_setting`.
- **Orgs and quotas.** The org list is `instance_list_orgs`. Leave a limit blank to keep it, type `none` to remove it, or give a number; the form is `set_quotas` and shows the limits it returns.
- **Projects.** `create_project`, and a project's sandbox snapshot and concurrency cap through `set_project_settings`. There is no instance-wide project list operation, so the project slug is typed (projects made in the session are suggested).
- **Backups.** Runs `db_backup` and shows the path, size and sha256 it returns. The file stays on the host: the page never offers a download.
- **Token.** Rotation runs `rotate_instance_token` after a confirmation. The new secret is shown once, with a copy button, and the page warns that the old token is revoked, so this session must sign in with the new one. The secret is held in memory only, never stored, and is gone when the screen is left.

## What stops an org reaching it

An instance operation takes the instance administrator and no one else: an org token of any role, a project-scoped token and a person (a member of any role) all get `forbidden`, whatever org they name. The reverse holds too: the instance token gets `forbidden` on every org operation. The [tenant isolation](/tenant-isolation) suite checks both for every principal it builds.

## Degraded network

A host can lose outbound network for minutes with the process alive. The probe is on by default for the daytona provider and off for docker and local hosts, which may have restricted egress by design; `TURNTABLE_NETWORK_PROBE` (`auto`, `on`, `off`) changes that. Every 15 s it resolves and sends a `GET /rate_limit` request to the configured forge API base (`poll.apiBaseUrl`, the host ingest uses) (and the sandbox provider's API for a remote provider). The probe fails when every target failed. Two failures in a row mean `degraded`; two successes mean healthy again. The state lives in the server process (a restart boots `unknown` until the first probe), each change is logged and audited, and `doctor` has an `egress` check, the admin pages show a banner, and `network_status` (MCP) and `instance_network_status` (REST) return it with the recent windows.

While degraded:

- No new attempt is claimed. The queue waits and resumes in its original order.
- An attempt that failed before its sandbox existed (a create failure, an unclassified error before the sandbox was recorded, or a controller lost with no sandbox) is requeued, not finished. It does not use the job's one automatic retry, and its check ends with the real result instead of `infra_error`. A job gets at most ten such requeues.
- An attempt that had a sandbox is never requeued this way, because it may have had side effects. It keeps the existing rule: one retry for a pull request job, none for a protected or release job.
- Check posts wait for recovery (up to 30 minutes each), then go out.

The probe never holds claims for good. Every step is bounded: a lookup or request that does not settle in time counts as a failure for that target. A degraded window also has a maximum length, `TURNTABLE_NETWORK_MAX_DEGRADED_SECONDS` (default 900). Past it claims resume with a logged warning and `doctor` `egress` fails, until the probe passes twice.

The job log of a requeued attempt starts with one line for each degraded window it waited through.
