A restart no longer has to wait for every running job. A running attempt whose job is already executing in its sandbox is handed to the next process, which re-attaches to it and records its real result with the complete log. Only attempts in a phase that cannot be handed off still need a drain.

## Which attempts survive a restart

An attempt is **adoptable** when act already runs in a live sandbox under a detached exec (its exec id is recorded) and it holds no credential that only the old process has. A restart hands it off: the job keeps running in the sandbox and the next process watches it to the end.

These phases are **not adoptable**, and a restart during them cuts the attempt as before:

| Phase | Why |
| --- | --- |
| Claimed, waiting for a sandbox | Nothing runs yet, and the create call belongs to the old process. |
| Creating the sandbox | The provider's create is in flight in the old process. |
| Setting up: egress canary, checkout upload, act install, action delivery | These are short calls the old process makes into the sandbox. They are not a detached exec. |
| A `release` job | Its release-lane credential belongs to the release lane, not to the controller, and is never rebuilt. Release-lane jobs stay not adoptable on purpose. |
| A job holding a GitHub token in its environment (a `protected` job with no secrets proxy) | The new process cannot rebuild the redaction of the token's encoded forms. |
| A job behind the secrets proxy on a free (unpinned) proxy port | The next process binds another port, so the sandbox's proxy URL would not reach it. |
| A job behind the secrets proxy, or holding an artifact credential, on a controller with no master key | Its credentials are random and live in the old process only. |

A job behind the secrets proxy (vault rules, its GitHub token, OIDC) or holding an artifact credential is **adoptable** when the controller has a master key and the secrets proxy has a pinned port (`TURNTABLE_PROXY_PORT`, or an advertised port). A free port differs in the next process, so those jobs stay not adoptable and the drain waits for them. The next process rebuilds each credential in memory and never reads one from storage:

- **Secrets proxy.** The proxy URL's password and the per-attempt CA the sandbox trusts are derived from the master key (its `adopt` domain), the org id and the attempt id. The next process registers the same credential for the same project policy (its proxy rules, passthrough hosts and the run's GitHub, OIDC and artifact targets), so the job's later secret-using steps keep working. It is compared on those inputs and a builder version (`PROXY_POLICY_VERSION`), not on the rules a build makes of them, so a deploy that only changes how rules are built does not refuse the attempts it takes over. Secret values still come from the vault per request.
- **Artifact credential.** The token the job holds is derived the same way and granted again for the rest of its lifetime.
- **GitHub token (behind the proxy).** The job never held it. The next process mints a new one with the permissions recorded when the first was minted, never wider. If the project is no longer live it gets exactly `contents: read` and `metadata: read`, as a fresh read-only token does. The old one is revoked when the old process hands the attempt off. After a crash it expires on its own. A controller that stalls but keeps running stops using the attempt's credentials (its GitHub token, OIDC and vault secrets) once its lease has lapsed by its own clock, less a margin of up to 2 seconds, before another process can take the expired lease and mint its own token. It uses them again only if a heartbeat renews the lease in time, and revokes the token once the database says the lease is lost. So two controllers' tokens are never both in use for one attempt, unless their clocks differ by more than that margin.
- **OIDC.** The proxy mints the credential per request from the master key, as before.

The attempt stores only what is needed to check this (`adopt_spec`): times, the token's permissions, a hash of the proxy policy, the proxy endpoint and a check value for each derived credential. It holds no secret. If anything differs at adoption (another master key, another proxy policy, another proxy endpoint, an expired credential, a token that cannot be minted), the attempt ends `infra_error` (a lost token or artifact credential reads `controller_lost (credential not re-established: ...)`; a lost proxy credential reads `re-attached attempt lost its secrets-proxy credential (...); not resumed`). The inherited sandbox is stopped and destroyed, and the job never runs on without its credential. The same holds when the egress policy refuses a re-attached attempt. Do not rotate the master key in the same restart as a deploy that hands attempts off.

A job with a cache grant is adoptable: after the restart its cache calls fail, which `actions/cache` reports as a miss on restore and a warning on save.

A blocked attempt is never handed off by a drain, but a crash or a drain timeout does not change how it ends: if its exec still runs at the next boot it is re-attached and keeps its real result, exactly as before, with one exception: a job behind the secrets proxy with vault rules and no stored spec still ends `infra_error`, because the new process cannot rebuild the proxy's registration. A `protected` job holding a token is never killed half-published by that.

A cut attempt is resolved by the next boot exactly as a drain timeout cut is: if its exec still runs, it is re-attached; otherwise it ends `infra_error` (`controller_lost`) and the job is requeued once under a new attempt, with no rerun used. A `protected` or `release` job cut after a step started is not requeued (see [Hosted](/hosted#deploying-without-killing-runs)).

## Deploying without a drain

1. Check `GET /api/v1/instance/drain` (`instance_drain_status`). `running_by_adoption` splits `running_attempts` into `adoptable` and `not_adoptable`.
2. Stop the old process with `SIGTERM`. It starts a drain (nothing new starts), hands off every adoptable attempt at once, and keeps handing off attempts as they reach that phase. It waits up to `drain_timeout_seconds` only for the rest.
3. Start the new process. Its boot reconcile re-attaches to every handed-off attempt at once: the old process expired their leases instead of leaving them to lapse.

When `not_adoptable` is 0 the restart waits for nothing. Otherwise it waits for those attempts, which are mostly a few seconds of setup. Keep the platform's stop grace period above `drain_timeout_seconds`.

## When a drain is still needed

Turn the drain on (`instance_drain`) and wait before the deploy when:

- `not_adoptable` stays above 0 because of `release` jobs, jobs holding a GitHub token in their environment, or a controller with no master key, and you do not want them cut. Wait for `running_by_adoption.not_adoptable` to be 0, not `running_attempts`.
- The deploy changes the database in a way the old and new process must not share (a migration with a manual step, `instance_db_copy`). Wait for `running_attempts` 0.

Several worker processes: drain or restart each one. A handed-off attempt is taken by whichever controller reconciles first. A job behind the secrets proxy is re-established only by a controller that advertises the same proxy endpoint and has the same master key. With workers that advertise different hosts or ports, drain the proxied jobs before a restart (wait for `running_by_adoption.not_adoptable` and `running_attempts` of those jobs to reach 0), or the peer that takes one refuses it and it ends `infra_error`.

## How a hand-off is safe

- **One owner at a time.** Every attempt has a lease (owner and expiry) that its controller renews. Another controller takes an attempt only when the lease has expired, in one conditional update, so of two controllers that try at once exactly one wins. A controller with a live lease is never displaced. A hand-off is the old owner expiring its own lease after its watcher has stopped.
- **Fenced writes.** Every log, step and result write checks the lease owner in the same transaction, so a controller that lost the lease cannot write into the attempt any more.
- **One watcher per process.** A process never runs two watchers for the same attempt.

## How the log resumes with no gap and no duplicate bytes

While it watches an exec, a controller records a checkpoint about once a second: an exec log offset and a stored log length, taken only at a line boundary with nothing held back for redaction, and written after every log write before it. At that point the stored log is exactly the rendering of the exec's output up to that offset.

The controller that re-attaches deletes whatever was stored past the checkpoint, reads the exec's output from the start to rebuild the step list and the verdict without writing anything, and writes only what follows the checkpoint. Its log is byte for byte what one controller watching from the start would have written. An attempt with no checkpoint yet (an older release) is replayed from the start instead, as before.

A live log viewer that had already shown text past the checkpoint sees it again after the re-attach.

The sandbox keeps a bounded amount of exec output (a head and a tail). If a job wrote more than that, the output in between is gone. The re-attach reads the exec from the start, so it rebuilds steps and the verdict from what survives and records a cut marker where output was dropped: a step whose events fell inside the dropped range is missing from the rebuilt list, as it would be for one controller watching the whole run.

## Why a job is queued

Each queued attempt carries a `waiting_reason`, shown by `get_run`, `job_steps` and the job page: `needs`, `project_cap`, `org_cap`, `instance_cap`, `quota:<metric>` (a held quota such as `quota:sandbox_minutes`, `quota:runs_per_hour` or `quota:concurrent`), `yield`, `drain`, `approval` or `claimable`. `needs` also covers a job held by its concurrency group or `strategy.max-parallel`. The claim pass records it from what it already read and writes only when the reason changes. `queued_ms_by_reason` splits the queued time by reason, and is final once the attempt starts. An attempt no claim pass has looked at yet has no reason. `yield` is a yield-class project waiting for capacity, which normal work has first call on. `approval` counts attempts held for an approval in `queued_by_reason` too, and the held time is booked to it when the approval releases the attempt.
