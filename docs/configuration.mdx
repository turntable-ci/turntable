## Formerly Longshore

For a few days this project was called Longshore. Nothing that ran under that name needs to change at once. Each old name still works, and most of them warn once at boot:

| Was | Now | What happens |
| --- | --- | --- |
| `LONGSHORE_*` environment variables | `TURNTABLE_*` | Read as the new name, with one warning per variable. If both are set, `TURNTABLE_*` wins and a warning says so. A value that the image sets itself (`TURNTABLE_HOST`, `TURNTABLE_DROP_PRIVILEGES`) therefore beats an old `LONGSHORE_HOST` or `LONGSHORE_DROP_PRIVILEGES` you set: rename those two. |
| `longshore.db` in the data directory | `turntable.db` | Renamed on first start (with its `-wal` and `-shm` files) when `turntable.db` does not exist. Back up the volume before the first start of a new version. |
| `__longshore_migrations` table | `__turntable_migrations` | Renamed in place (SQLite and Postgres), so no migration runs twice. A database with both tables is refused at boot with an error that names them. |
| `ls_` and `lsi_` tokens | `tt_` and `tti_` | Both prefixes are accepted. New tokens use the new ones. Only hashes are stored, so no token changes. |
| `longshore.v1` WebSocket subprotocol | `turntable.v1` | The server accepts both and echoes the one the client offered. |
| `longshore://runs/...` MCP resource URIs | `turntable://runs/...` | Both resolve. |
| `longshore.*` container labels, `longshore-run` sandbox label | `turntable.*`, `turntable-run` | New sandboxes get the new labels. Every list, count, reap and destroy path reads both, so sandboxes started before the upgrade are still found and cleaned up. |
| `--longshore-org` flag of `github-app create` | `--turntable-org` | Both work. |
| `longshore /` check run prefix | `turntable /` | New check runs use the new prefix. |

Fleet names such as `longshore-shadow` are configuration and stay as you wrote them. A fleet name may start with `turntable-` or `longshore-`. Signed or derived values never change with the name: webhook headers (`longshore-signature`, `longshore-event`, `longshore-delivery`, `longshore-cursor`), approval statement types (`longshore.approve_*.v1`), key-derivation and AAD contexts, and the provenance build type keep their original spelling, because existing secrets, approvals, signatures and receivers depend on it.

## Worker and provider flags

With `--worker`, `serve` also claims queued jobs and runs each in a sandbox from a provider.

| Flag | Default | Description |
| --- | --- | --- |
| `--worker` | off | Run the scheduler and worker in this process. |
| `--provider` | `docker` | `docker` or `daytona`. The server checks the provider at startup and exits with its name and the reason if it is unusable. |
| `--provider-config` | none | A JSON file of provider options. Secrets never go in it. |
| `--global-cap`, `--org-cap` | `4`, `2` | Most jobs at once, in total and per org. These are the `scheduler_global_cap` and `scheduler_org_cap` settings: set here they lock them, otherwise change them live (see [Instance admin](/instance-admin#sandbox-limits)). |
| `--image` | built in | The image jobs run in (Docker). |
| `--hosted` | off | This is a hosted, multi-tenant instance: every job needs a `microvm` or `vm` provider. Docker and Daytona sandboxes are containers, so with `--hosted` they are refused unless `--isolation-override` gives a reason. Also set by `TURNTABLE_HOSTED=1`. |
| `--isolation-override` | none | A reason. Lets jobs run on a provider weaker than their trust class requires. Audited and shown at the top of each affected job's log. |

```json
{
  "apiKeyFile": "/run/secrets/daytona-key",
  "baseUrl": "https://app.daytona.io/api",
```

| --- | --- | --- |
| `apiKeyFile` | none | Path of a file holding the API key. The key is read when first needed and never logged. |

| `fleet` | `longshore-dev` | Scopes the label, the name prefix and every count, list and delete to one fleet, so two instances on one account never touch each other's sandboxes. Lower case, starts with `turntable-`, at most 30 characters (for example `longshore-shadow`). |
| `maxLive` | `2` | Live sandboxes of ours at once. At most `10`. |
| `ttlSeconds` | `1800` | Longest sandbox lifetime. At most `1800`; longer requests are clamped. |

### Egress

Egress is deny by default, for every trust class. A job's sandbox has no network unless its run says otherwise: `none` unless the run's plan records `"egress": "open"` (or `"allowlist"`) from the project's configuration. Anything else is treated as `none`.

With `--worker` and with `turntable run`:

- A job is refused (as `infra_error`, naming the provider) when its provider cannot enforce the policy it asks for. That includes `none`: a provider that cannot cut the network is not trusted to. Docker and Daytona enforce `none` and `open`; neither enforces `allowlist` yet.
- A job that holds secrets is never run on `open` egress.
- Before a `none` job runs, a canary probe inside the sandbox tries a public IP and the cloud metadata IP (`169.254.169.254`). If either answers, the job is not run and ends as `infra_error`. If the image has no tool to probe with (curl, wget, nc or bash), the job runs with a note in its log, unless it holds secrets, in which case it is refused.

## Per-org quotas

An org can live under limits. Quotas limit tenants, so the **instance operator** sets them, on the host or with an [instance token](/instance-admin) over REST: `turntable quotas set --org <slug> --max-concurrent 3 ... [--data-dir ./data]` (`none` removes a limit; `turntable quotas show --org <slug>` prints them with usage). The only API operation that sets them is `set_quotas`, which takes the instance token and no org token, so an org's own tokens, operators and agents cannot raise their limits. They are read with `get_quotas` (REST and MCP, an org-level token; a project-scoped token is refused), which shows each limit, the usage against it and, for a limit that is reached, why new work is held:

- `max_concurrent`: attempts running at once. It can only lower this org's cap: the effective cap is the smaller of it and the instance's per-org cap (`--org-cap`), whatever a stored row says. Raise `--org-cap` to raise everyone's.
- `max_runs_per_hour`: runs that start in a rolling hour. A run that has already started finishes its jobs; new runs wait.
- `max_sandbox_minutes_per_day`: sandbox time in the last 24 hours, counted by the same function as the Usage page and `instance_run_summary`. Only an attempt with a recorded sandbox create time counts (one that never made a sandbox counts 0). It runs from the create to the confirmed destroy, else to the attempt's finish, and only a still-running attempt runs to now (marked `estimated`). An estimate never exceeds the attempt's recorded sandbox TTL, and the interval is clipped to the 24-hour window. The cap is checked when a claim is made, so it can overshoot by up to `max_concurrent` times a sandbox's lifetime (the attempts already past the check).
- `max_log_bytes`: stored job log bytes.
- `max_stored_bytes`: recorded artifact bytes plus control-plane cache bytes. (The cache also keeps its own per-class shares inside the org's cache quota; this is the org-wide total.)

`turntable quotas get --url <https://host> --org <slug> --token-file <file>` reads them remotely over the API (an org-level reader token), and the Quotas page of the UI shows each limit, its usage and percent, and why new work is held, refreshing as runs change. Both are read-only.

A reached limit holds new claims only: running attempts finish, queued ones wait until the window moves or the limit is raised. Null means no limit. Each metric emits an event when it first crosses 80% and when it is reached, once per window: a `quota.warning` or `quota.reached` event (org-level, not an `infra.error`), with the metric, used and limit.

## Settings registry

A setting is defined once in the settings registry (`packages/core/src/settings/`), the way an operation is defined once in the operations registry. One definition gives its key, scope (instance, org or project), type and validation, default, the role that may change it, whether MCP may change it, and its environment and TOML names. Secrets are never settings: they go to the [vault](/secrets-vault).

A setting has one effective value, resolved in this order, first match wins:

1. The environment variable named in the table below.
2. `turntable.toml`, from `--config <path>` or `TURNTABLE_CONFIG`.
3. The database, set with `instance_set_setting` or `set_setting`.
4. The default.

A value from the environment or from `turntable.toml` is locked: the set operations refuse it and name where it was set. The `get` and `list` operations return the value, its source (`env`, `toml`, `db` or `default`) and its lock. A setting that raises a limit or widens what a run may do is not changeable over MCP. An org or project setting flagged `instanceAdminOnly` (the Role column shows it) can be changed by the instance administrator only: `set_setting` refuses every org token, whatever its role, with "only the instance administrator can change `<key>`", and `instance_set_setting` sets it with `target_org` and, for a project setting, `target_project`. `set_project_settings` and `turntable policy set` are thin aliases with the same rules.

`turntable.toml` has the instance settings at the top level, then `[orgs.<slug>]` and `[orgs.<slug>.projects.<slug>]` sections for org and project settings. An unknown key or a bad value stops the boot, naming the key and the file. The file is optional: with none, the compiled binary boots from an empty directory.

```toml
[backup]
keep = 20
```

Only some settings are on the registry so far; the rest are still read straight from the environment. Org and project settings in the table below can be read and changed in the web UI: see [Settings in the web UI](#settings-in-the-web-ui).

## Settings in the web UI

Org settings are under **Org settings** in the sidebar, and a project's settings are on its **Settings** page. Both are generated from the registry through `list_settings`, so a setting that is added to the registry appears with no UI change. The UI has no instance settings page yet: the instance settings are changed with the `instance_` operations, the environment or `turntable.toml`.

Each field shows its effective value, its source as a badge and whether it is locked:

| Badge | Meaning |
| --- | --- |
| `env` | An environment variable sets it. Locked: "Set by TURNTABLE_X". |
| `toml` | `turntable.toml` sets it. Locked: "Set in turntable.toml". |
| `ui/db` | A value saved through the UI or `set_setting`. |
| `default` | Nothing sets it, so the registry default applies. |

A locked field is read-only: change it where the note says. An unlocked field is editable by a member whose role meets the setting's own role, and never below operator. Other members see it read-only with the role it needs. Saving calls `set_setting` and shows its refusal (locked, role or a value that fails the setting's type) as the server wrote it; the page does not validate values itself. After a save the list is read again. **Reset to default** removes a stored value.

| `TURNTABLE_REQUIRE_ORG_KEYS` |  | off | Set to `1` after `turntable keys reseal` has run for every org: a sealed record that is not under its org's own key is then refused wherever the org is known, and `keys reseal` itself refuses to run while it is set.
