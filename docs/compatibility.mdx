title: Compatibility
description: Which GitHub Actions features Turntable supports, and how it reports the rest.

Turntable promises that unsupported features fail loudly at parse or plan time. It never silently ignores them. Every feature is in one of three states.

| State | Meaning |
| --- | --- |
| Supported | Behaves as on GitHub. |
| Supported with differences | Works, with documented differences. |
| Unsupported | Rejected with an error that names the feature. |

<Note>
  Turntable runs workflows through [act](https://github.com/nektos/act), one job per sandbox. The table below says what v1 supports; rows still being proven against real workflows say so.
</Note>

## Pull request events

Steps see the event as they do on GitHub where it matters: act is given a `github.event` payload built only from forge facts fetched at poll time. For a pull request it carries `number`, `pull_request.number`, `title`, `body`, `labels[].name`, the real `draft` flag, `user.{login, type}`, `base.{ref, sha, repo.full_name}`, `head.{ref, sha, repo.{full_name, fork}}`, a top-level `sender.{login, type}` and `repository.full_name`. `sender` is the pull request author, which is what GitHub reports for an opened or synchronize event; it is not the person who last pushed or labeled. `head.repo.fork` is the head repository's own `fork` flag, as GitHub reports it. The body is capped at 64 KiB (cut at a character boundary, no marker added) and at most 100 labels are kept. For a push it carries `ref`, `before`, `after` and `repository.full_name`. Merge group events are unchanged. The payload is stored with the run, so a re-attach or a rerun sees the same bytes. Tokens and any other field are never included. The title, body and label names are text the pull request author controls: Turntable only writes them into the event JSON file act reads, never into a command line, an environment variable, a log line or a check summary, and `${{ }}` inside them is data that nothing evaluates. Plan-time `if:` expressions read the same facts, but the planner does not support the `labels.*.name` object filter yet, so a job gated that way is kept (never skipped) and act evaluates it. The delivered checkout has an `origin` remote (`https://github.com/<owner>/<repo>`, never with credentials), as `actions/checkout` leaves it, so `git fetch origin <sha>` works when the job has network egress.

**Known difference: poll time, not event time.** A pull request is judged by its state when Turntable sees it, not by the payload of each GitHub event. A GitHub App webhook only wakes the poller early; it does not carry its own payload into the run. So a commit pushed while the PR is a draft, and marked ready before Turntable next looks, runs with the ready verdict. GitHub skips that `synchronize` event and runs at `ready_for_review` instead. The outcomes converge; Turntable can simply run earlier. A draft or ready flip at a head Turntable already handled triggers a new run when the workflow's `types` include that action.

**Known difference:** GitHub runs `pull_request` workflows on the merge commit (`refs/pull/N/merge`). Turntable runs the pull request head sha. This is deliberate for now, and `github.sha` is the head sha.

## Support

| Feature | Status |
| --- | --- |
| Triggers: `push` (branch and tag filters, `paths`), `pull_request`, `merge_group` | Supported, see [Quickstart](/quickstart) |
| Triggers: `workflow_dispatch` | Supported through the `run_dispatch` operation (REST and MCP), see [Manual runs](#manual-runs-workflow_dispatch) |
| Triggers: `schedule` | Not ingested yet |
| `needs`, job outputs, `matrix` (with `fail-fast` and `max-parallel`), `if:`, `continue-on-error` | Supported |
| `matrix` built from `fromJSON(needs.<job>.outputs.<name>)` | Supported. The job expands when its needs finish, with GitHub's `include` and `exclude` rules and a limit of 256 combinations. An empty matrix skips the job; invalid JSON or more than 256 combinations fails it. |
| `concurrency` | Supported with differences: groups are scoped to the repo, and a pull request run's group is rewritten so it cannot cancel the default branch, see [Security](/security#trust-classes-and-fork-pr-gating) |
| Composite and JavaScript actions | Supported, resolved to a commit sha before the run, see [Security](/security#action-pins-and-moved-tags) |
| `GITHUB_OUTPUT`, `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_STEP_SUMMARY` | Handled by act |
| Reusable workflows | Not yet verified |
| `actions/checkout` with `submodules: true` or `recursive` | Supported with differences: the controller fetches each submodule at its pinned commit (depth 1) and delivers it with the repository, see [Submodules](#known-gaps). `false`, the default, fetches nothing extra. |
| `services:` and `container:` jobs | Supported on a Docker-capable size class the operator configures (see [Docker-capable class](/providers#docker-capable-class-services-and-container-jobs)). Without one, or on a provider that cannot run Docker, the job fails with the reason. An untrusted pull request does not get one unless the operator opts in |

## Manual runs (`workflow_dispatch`)

A workflow that declares `on.workflow_dispatch` is started with the `run_dispatch` operation (REST `POST /api/v1/dispatches`, or the MCP tool of the same name), for a repo the project ingests. There is no polling for it: a run exists only when someone asks.

- **Who:** a token or member with the `release_operator` role or higher (the maintainer tier). An `operator` or a `reader` is refused. Every call is audited with who, the workflow, the ref, the resolved sha and the input **names**; input values are never written to the audit log, because they may be sensitive. They are stored with the run.
- **Ref:** a branch or tag name of the repo (or a full `refs/heads/...`, `refs/tags/...`). A bare commit sha is not accepted, as on GitHub. It is resolved to a sha when you call, in the repo itself (a fork's branch or an unknown name is refused with the reason), and the run is for exactly that sha. The workflow file is read at that sha.
- **Inputs:** a map of strings, checked against `on.workflow_dispatch.inputs`. Unknown names are refused, `required` inputs without a default must be given, defaults are applied, `boolean` takes `true` or `false`, `number` a number, `choice` one of its `options`, and `environment` an environment name. At most 25 inputs and 64 KiB in total. Jobs see `github.event_name == 'workflow_dispatch'`, `github.event.inputs.*` as strings (as GitHub does) and `inputs.*` typed. A workflow with no `on.workflow_dispatch` is refused.
- **Trust class:** the same decision as any run, with the dispatching role standing in for a maintainer. The default branch, and the project's protected refs, are `protected`. Any other branch (or a tag that is not a release ref) is `trusted_pr`, without secrets. A tag the project lists in its release refs is a `release` run and **waits for approval** before any job starts, exactly as a tag push that no ruleset protects does; a dispatch never skips an approval. A dispatched run that is not the default branch also gets its own concurrency group, so it cannot cancel the default branch's runs.
- **Agent tokens (`run_dispatch_agents`):** a protected or release run can hold deploy credentials, and an agent chooses its inputs after reading untrusted text, so a project limits what a token of kind `agent` may dispatch (the same notion of agent as `untrusted_run_approval = no_agents`). `unprivileged` (the default): only a run below `protected`, so a feature branch yes, the default branch, a protected ref or a release tag no. `none`: no agent dispatch at all. `any`: allowed, and a release run still waits for its human approval. The refusal comes BEFORE any forge call, from the ref name and the project's own config (default branch, protected refs, release tag patterns), with `agent tokens may not dispatch protected or release runs in this project (run_dispatch_agents)` (`agent tokens may not dispatch runs in this project (run_dispatch_agents)` under `none`); it is checked again with the real class once the ref resolves, and nothing is created. A person's token is never limited by it. Like `untrusted_run_approval`, an org owner may tighten it (`any` < `unprivileged` < `none`), only the instance administrator loosens it, and it cannot be changed over MCP. See the [configuration reference](/configuration).
- **Visible:** the run's `event` is `workflow_dispatch` and its `actor` is the dispatching principal, in `list_runs`, `get_run` and the checks posted for it. It counts against the project's hourly run cap.

- **Run title (`run-name`):** the workflow's `run-name` is evaluated at plan time with the `github` and `inputs` contexts (typed inputs print as GitHub prints them) and stored as the run's display title. It shows in `get_run` and `list_runs` (`run_name`), the run list, run page, job page and command palette in the UI, and every check run: the title carries it in parentheses and the summary has a `**Run:**` line (the check name is unchanged, so required-check gates still match). An expression that reads another context (`vars`, `secrets`, `env`), calls `hashFiles` or fails to evaluate falls back to the default title, silently. Workflows with no `run-name` are unchanged. Push and pull request runs use it too.

Differences: the `workflow_call` form of inputs is not read, and the run needs a poller in the same process as the server that takes the call (the default `serve` roles).

## Splitting a job across sandboxes

A heavy job can run as several shards, each in its own sandbox, **without editing the workflow**. The operator configures it per repo (`splits` in the poll config, or `turntable policy set --ingest on ... --splits-json '<json>'` for a bound repo); it is never read from the repository, so a pull request cannot change it.

```json
"splits": [{
  "job": "tests",
  "shards": [
    { "steps": ["Audit engine tests"] },
    { "steps": ["Rules tests"] },
    { "steps": ["Remaining package and script tests"] }
  ]
}]
```

`job` is the job id. Each shard lists the steps (by `name:`, or `#<n>` for the nth step counted from 1) that run only there; 2 to 8 shards, and a step may be in one shard only. Every other step (checkout, setup, anything the rule does not name) runs in every shard, so each shard sets itself up. The only change made to a shard's workflow is `if: false` on the steps another shard owns: no step is added or edited. A step the rule names that no longer exists (a pull request renamed it) is owned by no shard, so it runs in all of them: coverage is never lost, only time.

- **One job to everything else.** The shards are ordinary jobs (`tests[0]`, `tests[1]`, ...) with the job's own name. `needs` waits for all of them; `needs.<job>.result` is the fold (failure if any shard failed, else infrastructure error, cancelled, skipped only if all were, else success); outputs merge with a later non-empty value winning. The forge sees **one check, under the job's name**, running until the last shard finishes, with the fold as its conclusion and each shard's result in its summary. In the UI the run page shows the shards as one job row (its name, the folded state and the wall time) that opens to one row per shard, with the step it owns, its attempts, its duration and its own rerun. `turntable parity` treats the shards as one job and reports the wall time from the first shard's start to the last one's finish, not the sum.
- **Failure.** Shards never cancel each other (a job's steps already run every suite even when one is red). An infrastructure error in one shard is an infrastructure failure of the job. Cancelling the run cancels every shard. A shard can be rerun alone (the others keep their results); the rerun reports its own check with the fold of the latest result of each shard.
- **Limits.** Each shard counts against the project's and the org's concurrency caps like any job, and pays its own setup. A job with `strategy.matrix`, or whose declared outputs read the output of a step a shard owns, is not split and runs whole; the run's plan says why (`splitNotices`).

- **Running only the shards whose paths changed.** A shard may carry `paths`, a list of globs in the workflow path-filter syntax (`!` negation included, the last matching pattern decides): `{ "steps": ["UI tests"], "paths": ["packages/ui/**", "!packages/ui/docs/**"] }`. The shard runs only when a changed file matches; a shard with no `paths` always runs. An empty list or a bad glob is a config error when the config loads.
  - **Which files.** The same set the workflow's own path filters use: a pull request's diff against its base, a push's before..after, and for a merge group the queue commit against the group's base. A rename counts under its old and its new path, and a deleted file under its path. The files come from the forge's compare of the commit range at ingest, never from the repository, so a pull request can only change which shards run through its own diff, never the config.
  - **Unsure means run.** With no before commit (a new branch, the first push seen), a force push that removed the base, a compare that failed, a diff larger than one poll will page through, or an empty list, every shard runs. A partial list is never used.
  - **Recorded once.** The decision is stored in the run's plan at ingest, and the run's plan notice names its source (for example `shards selected by changed paths (push a1b2c3d4e5f6..d4e5f6a1b2c3, 12 files)`). A rerun of the run, of the job or of one shard uses the stored decision and never asks the forge again. A skipped shard's log says which paths it listed and none changed.
  - **Results.** A skipped shard is ignored by the fold. If every shard is skipped, the job is `skipped`: it reports to the forge exactly as a job skipped by `if:` does (no check is posted), and `needs:` consumers see a skipped job, so a job that needs it with the default `if:` is skipped too. `turntable parity` takes the wall time from the shards that ran.
  - **Not a gate.** A shard limited by `paths` is not a gate for files outside its globs. Do not put a security check behind a path rule unless its globs cover everything it checks.

## Artifacts

`actions/upload-artifact` and `actions/download-artifact` (v4 and up, including the v7 and v8 that Turntable's own release workflow pins) work inside a run when the control plane has an artifact store. Set `TURNTABLE_ARTIFACTS_URL` to the base URL sandboxes reach the control plane at (the same kind of address as `TURNTABLE_CACHE_URL`). act's own artifact server speaks only the old v3 protocol, so Turntable serves the one these actions use: the twirp `ArtifactService` at `ACTIONS_RESULTS_URL`, with Azure block-blob requests for the bytes. upload-artifact v7 and download-artifact v8 both ship `@actions/artifact` 6.3.1. Against v4's client (2.x) it adds `version: 7` and a `mimeType` in `CreateArtifact`, a `digest` in `ListArtifacts` that download-artifact checks against the bytes it received (the step fails on a mismatch), and `archive: false`, which uploads one raw file under its own name instead of a zip. All are handled. Each job gets `ACTIONS_RESULTS_URL` and a per-job `ACTIONS_RUNTIME_TOKEN` for its attempt, which stops working when the attempt ends. The token is redacted from the log. It also travels in the blob URL paths (`/_artifacts/`), so access logs should not record those paths.

- **Scope.** The run, project and org come from the job's token, never from the request. A job reaches only the artifacts of its own run. Downloading from another run (`run-id`, `github-token`) goes to GitHub's API, not here, and is not supported.
- **What is stored.** The client's upload (a zip, or with `archive: false` one raw file), as one blob under `<data dir>/artifacts/<run id>/<name>`. The control plane streams it to disk, hashes it itself (sha256), compares the client's reported hash and size, then records it against the run, job attempt, name, size and digest. A mismatch is refused and nothing is recorded. A name is recorded once per run: a second upload of the same name, `overwrite`, and `delete-artifact` are refused. Names are one plain component of letters, digits and `. _ + -`, up to 200 characters, so an `archive: false` file with a space or other character in its name is refused. A download is served as `application/zip` when the stored bytes start like a zip and as `application/octet-stream` with a `Content-Disposition` file name otherwise; what the client said its `mimeType` was is not used.
- **Limits.** The org's stored-bytes quota (shared with the cache) and `TURNTABLE_ARTIFACT_MAX_GIB` (default 2). An upload that would pass either is refused with a message in the job log.
- **Trust class.** An artifact carries the trust class of the attempt that wrote it. A download is decided against the class of the job reading: the same class or a higher one reads it, a lower class's artifact is refused (the actions have no way to ask for a lower class's artifact explicitly), and a `release` job reads only `release` class artifacts. The refusal is a line in the job log and the artifact looks absent. The digest is recomputed from the stored file before every download, and a mismatch is refused.
- **Retention.** `TURNTABLE_ARTIFACT_RETENTION_DAYS` (default 90) for the whole instance. After it the bytes are removed and downloads fail. The recorded digest stays.
- **Reach.** A job with open egress reaches the store directly, as for the cache, with a credential that can upload and download. A job with egress `none` has no network, but the artifact service is Turntable itself, so a job whose plan has an `actions/upload-artifact` step (read from the plan, so a composite action or a reusable workflow that wraps it is not seen) gets a narrow route through the [secrets proxy](/secrets-proxy): only `POST` of `CreateArtifact` and `FinalizeArtifact` and `PUT` of a blob upload, on the control plane's host and port, and nothing else (every other host, port, method and path is refused by the proxy). Its credential is **upload-only**: it lives at most two hours and for the attempt, and the service refuses it listing, download URLs, deletes and downloads. A job like that cannot download artifacts. This needs `TURNTABLE_SECRETS_PROXY=1`, an `https` `TURNTABLE_ARTIFACTS_URL` whose address is public (the proxy only dials public addresses), and a provider that can confine the sandbox to the proxy (see the table in [Secrets proxy](/secrets-proxy#how-a-job-reaches-the-proxy)); on a provider that cannot, a job with an upload step ends as `infra_error` rather than running with a different network. Without the proxy, a job with egress `none` gets no artifact credential and the actions fail with a missing `ACTIONS_RESULTS_URL`.
- **Release lane.** Set `TURNTABLE_RELEASE_ARTIFACT_DIR` to `<data dir>/artifacts` and the lane signs from what the jobs uploaded. See [Release lane](/release-lane#artifacts-from-jobs).
- **Not supported yet.** Encryption at rest (unlike the cache, the directory is plaintext, so use an encrypted volume), a per-project retention, and downloads from a job with egress `none`.

## Checks mode and onboarding

Each project has a `checks_mode` setting that decides what Turntable reports to GitHub as check runs:

- Off: runs on Turntable, posts nothing to GitHub (default)
- Shadow: posts neutral `shadow / <job>` checks that never block
- Live: posts `turntable / <job>` checks your rules can require

In the settings and ops the values are `off`, `shadow` and `live`. Setting any of them through an op needs the org owner or admin role, and only people can do it: no agent token holds admin. `turntable policy set --checks-mode` at the host does the same and refuses a value that `turntable.toml` or the environment locks.

It is stored in the project's `checks_mode` column, the same one `turntable policy set --checks-mode` writes, so what the settings ops show is what the reporter does. A value in `turntable.toml` (`orgs.<slug>.projects.<slug>.checks_mode`) locks it: the reporter follows the file and the ops refuse to change it. A project nobody set stays `off`, so no existing project changes mode.

Turning checks on does not leave finished work unreported. When the mode changes from `off` to `shadow` or `live`, or from `shadow` to `live`, Turntable takes the project's latest run for each repo, ref and workflow (the default branch and the pull request heads it has seen, within three days) and posts every job's current state as that mode's check: the final conclusion for a finished job, `in_progress` for a running one, `skipped` for a skipped one. The checks use the same external ids as the live events, so a job's later events update the check and never add a second one. Going from `shadow` to `live` posts the `turntable / <job>` checks beside the neutral `shadow / <job>` ones, which stay as they were. A change to `off` posts nothing. Each backfill is recorded in the audit log as `checks_backfill`, and a restart does not repeat it. It starts from a change made through the settings ops or `turntable policy set`; a mode set by `turntable.toml` or the environment is not backfilled.

Side by side runs hold read-only tokens. While a project is `off` or `shadow`, a job's `GITHUB_TOKEN` is capped to `contents: read` and `metadata: read` (or unset on a public repository), so a workflow that comments on issues or creates a release cannot repeat those writes next to GitHub Actions. Its log says `shadow: GITHUB_TOKEN write permissions lowered to read`. Going `live` gives jobs the permissions their workflow declares. See [security](/security).

The onboarding ops use it. `list_installation_repos` shows an installation's repos with their project, mode and paused state. `onboard_repos` (owner or admin session) adds each ticked repo that is not a project yet (the same code as `add_project`) and turns CI on for a batch of repos in one transaction: `max_concurrent` 2, PR mode `allowlist` with the caller's GitHub login, no bots, the project variable `TURNTABLE_CI=true` and the chosen checks mode (default `off`: posts nothing until someone picks `shadow` or `live`); a repo left unticked is paused with `max_concurrent` 0. `preview_workflows` runs the planner over the default branch's workflow files without running anything and says, per job, whether Turntable would run it, skip it or fail it, with a fixed fix for each failure kind. `run_default_branch` starts one push run of the default branch's head, protected like any default-branch push, once per sha.

To keep a job Turntable cannot run off Turntable, gate it on the variable the onboarding sets: `if: vars.TURNTABLE_CI != 'true'`.

## Runner labels

What a `runs-on` label does on Turntable:

| Label | Result |
| --- | --- |
| `ubuntu-latest`, `ubuntu-24.04`, `ubuntu-22.04` | The default sandbox class (unless the operator maps the label). |
| `ubuntu-latest-{2,4,8,16}-cores` | A class with that many cpus, only among the operator's `coresClasses`; else the default class. |
| Custom labels (`boat`, `large`) | The operator's label map, else the default class. Always Linux. |
| `macos-*`, `windows-*`, `[self-hosted, macOS]`, `[self-hosted, Windows]` | Refused. The job never reaches a sandbox and its check **fails**. |
| `arm64`, `*-arm` | Refused unless the provider advertises arm64. Daytona offers amd64 only. |

**Per-org and per-project overrides.** The operator's label map is the default. An org (`runner_labels`) or a project (`project_runner_labels`) may map its own labels, including `ubuntu-latest`, to a size class the operator defined: the project's map beats the org's, which beats the instance map. A tenant cannot name a class the operator did not define, nor one marked `tenantSelectable: false` unless the org is in that class's `orgs` (checked when the map is set and again when the job runs; a stale entry fails the job with a reason, before any sandbox is created, and never falls back to the instance map or `default`), and the operator's ceilings still apply. An untrusted pull request always gets the operator's `untrustedClass`. Each class is realised per provider (a Daytona snapshot, a Docker image); a provider that cannot realise the class fails the job with the reason. See [Sandbox size per job](/providers#sandbox-size-per-job).

A refused job fails instead of being skipped on purpose: GitHub branch protection counts a skipped or neutral required check as passing, so a skip would let a pull request merge without the job ever running. The check summary names the label and says `If this job should stay on another CI, gate it with if: vars.TURNTABLE_CI != 'true'`. A job whose own `if:` is false (the gate above, set on the project) is a normal skip: that is the explicit opt-out. The same rule covers every job Turntable cannot run (docker, `services:`, `container:`).

## Known gaps

Everything found while running real workflows. Each one is a gap with a stated behaviour, not a silent one.

- **`pwsh` exists only where the image has it.** The Turntable runner image includes PowerShell 7. A provider that starts from its own snapshot (Daytona, for example) has `pwsh` only if that snapshot does. A tool that is missing is absent as on a runner without it, so a workflow's own probe works: `if ! command -v pwsh; then echo "::notice::skipped"; exit 0; fi` skips and succeeds. A step that needs it without a probe fails with exit 127 and a log line naming the tool.
- **`services:` and `container:` jobs run on a Docker-capable class.** The operator defines a size class with `"docker": true` and names it as `dockerClass` in the sandbox size map. A job that declares `services:` or `container:` is routed to that class and run by act in its container mode, so real service images, health checks and ports work; every other job in the run stays in host mode on its own class. Before act starts, Turntable checks inside the sandbox that `docker info` succeeds; if it does not, the job fails as an infrastructure error. Egress is unchanged: the sandbox is still the boundary, and images are pulled through its egress. With egress `none` an image that is not already in the sandbox cannot be pulled, so the job fails naming the image (preload it in the class's snapshot); egress is never widened for it. If no `dockerClass` is configured, the provider cannot run Docker inside a sandbox, or the run is an untrusted pull request and `untrustedDocker` is not set or the provider is not microVM-isolated, the check fails with `uses services:` (or `uses container:`), the reason, and the gating hint below, never `skipped`. A tenant cannot map a label to the docker class unless the class is `tenantSelectable` or the org is in its `orgs`. Limits of this first version: a job in container mode cannot use the secrets proxy (it fails with that reason), and its declared job `outputs:` are not read back yet.
- **Docker as a command or action.** Container mode hands a job no daemon socket, so a job that runs `docker` itself, uses a `docker://` image, a `docker/` action, or a local docker action is still refused by the planner and its check fails with the reason (`docker` as a command, a `docker://` image, a `docker/` action, a local action that is a docker action or runs docker), with the reason. It cannot see a docker call hidden inside a script such as `bun run test:integration`, so that job starts and fails when the command runs. To keep such jobs off Turntable, gate them with a project variable: set `TURNTABLE_CI=true` on the project (`turntable policy set --ingest on ... --var TURNTABLE_CI=true`) and write `if: vars.TURNTABLE_CI != 'true'` on the jobs that need docker or services. GitHub has no such variable, so the job runs there as before. The opposite gate (`if: vars.TURNTABLE_CI == 'true'`) adds a job that runs only on Turntable, for example a variant of a database test that runs in-process.
- **Interpreters that a setup action puts first get no shim.** Turntable puts a shim on `PATH` for `node`, `python` and `pwsh`, which keeps steps off a terminal and makes `command -v` behave as on GitHub. The shim is linked only for an interpreter that exists, so `command -v` fails for one that is absent. Each shimmed step re-checks at start and at exit and links a shim for a tool installed behind the shim directory during the job (for example `pwsh` installed with apt), so it is wrapped from the next shimmed step on. It never removes a shim and never shadows a directory placed ahead of the shims. An interpreter that `setup-node` or `setup-python` puts first on `PATH` is not shimmed, so a later `shell: node` or `shell: python` step runs with act's terminal and may differ from GitHub in terminal-dependent output.
- **`export-ignore` is not honoured.** A run's checkout is the whole commit, fetched and packed in process, which is what `actions/checkout` gives. The earlier path used `git archive`, which honours `export-ignore` in `.gitattributes`, so files a repo marks that way are now present where they were absent before. If a workflow relied on them being absent, it needs an explicit step.
- **`actions/checkout` with `fetch-depth: 0` (or deeper than 1, or `fetch-tags: true`) gets the full history.** The controller delivers depth 1 by default. A job whose checkout step asks for more is fetched again with the whole history of the run's commit, every tag, and the default branch as `refs/remotes/origin/<default>` and `refs/heads/<default>`; the `shallow` file is absent only then. The same caps apply, with the pack, unpacked and tarball budgets at four times the shallow tree's (per project, `project_checkout_max_unpacked_mib` and its siblings raise them, up to the instance ceiling; see Configuration), and a budget hit ends the job `infra_error` with kind `fetch_limit`, naming the limit, its value and the setting that raises it (`TURNTABLE_CHECKOUT_MAX_PACK_MIB`, `TURNTABLE_CHECKOUT_MAX_UNPACKED_MIB`, `TURNTABLE_CHECKOUT_MAX_TARBALL_MIB`, `TURNTABLE_CHECKOUT_TIMEOUT_SECONDS`, `TURNTABLE_CHECKOUT_MAX_MEMORY_MIB`, at most 500 000 objects and 10 000 tags), and a repository over one fails the job with `fetch-depth 0 needs the full history, which could not be delivered for this run: <reason>`; it is never cut down to a shallow one. The `fetch-depth: 1` default is unchanged.
- **`actions/checkout` with `submodules: true` or `recursive` is fetched by the controller, from github.com only.** A job whose checkout step asks for submodules gets each gitlink's pinned commit at depth 1, delivered under `.git/modules`, and the stand-in's offline `git submodule update --init` then checks them out. A same-owner module is fetched with an installation token for that one repository (`contents: read`), only when the installation covers it and the run is trusted (a push, a merge group or a trusted pull request); an untrusted run (an outside author's pull request, even an approved one) fetches every module anonymously, as a fork pull request's token reads only its own repository on GitHub. Any other module is fetched anonymously, so a private repository of another owner fails with a message that names the submodule. A url that is not `https://github.com/<owner>/<name>` (ssh, scp-style, `http`, another host, a credential or option-like text) is refused, as is a `.gitmodules` whose names or paths could leave `.git/modules` or the tree. `recursive` follows modules of modules (up to 8 deep). Every checkout cap is one budget shared by the repository and its modules (files, pack and unpacked size, objects, tarball size, wall clock, and at most 64 modules in all), and a module that cannot be had fails the job: nothing is delivered half-way. A step that runs `git submodule update --init` itself (no `submodules:` input) still clones over the network with no credential.
- **Job splitting is configuration, not workflow syntax.** A heavy job is split across sandboxes by an operator rule (`splits`), never by anything in the repository, so a pull request cannot change it. See [Splitting a job across sandboxes](#splitting-a-job-across-sandboxes). A job with `strategy.matrix` is not split, and a step a rule names that was renamed runs in every shard.
- **Pull requests run the head commit, not the merge commit,** as described under [Pull request events](#pull-request-events).
- **`schedule` is not ingested yet,** and reusable workflows are not yet verified (see the table above).

## Runner image toolset

GitHub's `ubuntu-latest` image comes with a large preinstalled toolset, and workflows assume it. Turntable's sandbox is a smaller image, built from `images/runner/Dockerfile`: the pinned `node:22-bookworm` base plus PowerShell 7 (pinned by version and checksum), `jq`, `rsync`, `zip`, `unzip` and `sudo`. A step that needs a tool the image lacks fails with exit 127, and the log says `<tool> is not available on this image` so it is not a bare "command not found". A tool the image lacks is simply absent, as on a runner without it: `command -v pwsh` fails, so a workflow's own probe (`if ! command -v pwsh; then echo ::notice::skipped; exit 0; fi`) skips and succeeds. Turntable puts a shim on `PATH` only for the interpreters that exist (it uses them to keep steps off a terminal), never for one that does not. Install the tool in a step if egress allows it, or use your own image.

This table is generated from the built image in CI (`scripts/runner-toolset.ts`), so it cannot drift from the image. "On GitHub" is whether `ubuntu-latest` has the tool preinstalled.

### Job user and sudo

GitHub-hosted runners run steps as a user with passwordless `sudo`, and workflows rely on it (`sudo apt-get install ...`). Every Turntable provider matches that: the job runs as root with a working `sudo`, or as a user with passwordless `sudo`. The runner image runs steps as root and ships `sudo`, so a literal `sudo apt-get install ...` works with no password. A snapshot or image that does not meet this fails such workflows with `sudo: command not found` or a password prompt. To check one, run this inside a sandbox from it:

```sh
id -u; sudo -n true && echo sudo-ok
```

It must print `sudo-ok` (a uid of `0` alone is not enough, because the `sudo` binary must exist). The live egress probe records the same check per class, see the providers page.
